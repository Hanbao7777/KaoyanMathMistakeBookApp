# TickTick P0 Closure Design

## Background

TickTick 模块已经完成了多轮修复与测试补洞，但当前真正影响交付的仍然是 P0 级问题：主流程页面是否稳定显示、侧边栏工具区是否正确定位、启动环境问题是否有清晰收口。

从现有 `TICKTICK_KNOWN_BUGS.md`、`KNOWN_ISSUES.md` 与 `ROADMAP.md` 看，TickTick 仍被定义为当前阶段重点，且这三份文档目前**仍把三项 P0 描述为“待修复”**。但对源码的核对显示：布局与工具区定位两类 P0 的代码改动**已经落地**（详见下文 “P0 问题清单与真实状态”），文档与代码已出现漂移——这正是本轮要收口的核心风险：把“曾经的问题”误当成“仍然的问题”。

因此在继续做 P1/P2 之前，先做一轮 **TickTick P0 重新验收与闭环设计**，把“哪些问题已解决、哪些仍未解决、每项如何验收和收口”钉死。本文档只做重新验收与闭环设计，不写实现计划，也不改任何源码或状态文档；文档漂移的修正留到下一步实现/文档同步计划里执行。

## Goal

为 TickTick P0 问题建立一份可执行的重新验收与闭环设计，明确：

- 当前 P0 问题清单
- 每项问题的真实状态（已修复待验收 / 未修复 / 仅有 workaround）
- 推荐修复顺序
- 每项最小验收标准

## Non-Goals

- 不直接实现 P1/P2 修复。
- 不扩到 TickTick Phase 2 占位功能补齐。
- 不扩到错题本、AI/OCR、renderer/E2E 总体测试策略。
- 不推进 `databaseService.ts` / `registerIpc.ts` 之类的大型架构重构。

## Scope

### In Scope

- TickTick 主内容区 / 根容器布局
- 侧边栏工具区定位
- 打包版 / exe 启动环境问题的收口方式
- P0 页面级可见性与可用性验收范围：
  - Today
  - Calendar
  - Inbox
  - List Detail
  - Focus
  - Settings

### Out of Scope

- P1 数据完整性修复实现
- P2 体验和维护项实现
- Phase 2 占位功能补齐

## Constraints

- 先做“重新验收与闭环设计”，不直接进入修复实现。
- 必须区分“代码可能已修”与“已完成稳定验收”。
- 验收标准必须落到可观察页面行为，不写泛泛表述。
- 文档收口应能直接转成下一步实现计划，不重复做大范围产品路线图。

## Proposed Approach

### Approach A — P0 单独收口（推荐）

先把 TickTick P0 单独做成一个小闭环：重新盘点问题、逐项确认状态、明确验收标准，再决定哪些项需要真正修复，哪些项只需要文档或手工验收收口。

优点：

- 能最快回答“TickTick 主流程现在到底稳不稳”
- 避免 P0/P1/P2 混在一起导致修复顺序混乱
- 有利于下一步直接生成执行计划

### Approach B — P0/P1 一起重排后统一做

信息更全，但当前会把“页面能否正常打开显示”和“数据是否安全”两类问题搅在一起。首轮不推荐。

### Approach C — 直接开始修 P1，默认 P0 已经差不多

风险最高。如果 P0 其实还没闭环，后续所有 P1 修复都会建立在不稳定 UI 主流程上。

## Recommended Design

采用 **Approach A**。

P0 收口按 3 类问题重新确认。状态口径固定为三选一：**已修复待验收** / **尚未修复** / **需 workaround / 文档收口**。下方每项的“真实状态”是对本次源码核对的记录，仍需由实现者在打包版里做一次可观察验收后才能标记为“已闭环”。

### P0 问题清单与真实状态

#### P0-1 主内容区宽度被挤成 ~12px（布局与显示）

- **文档现状**：`TICKTICK_KNOWN_BUGS.md`、`KNOWN_ISSUES.md` 仍描述为待修复。
- **代码核对**：`src/renderer/App.tsx` TickTick 分支外层已用 `className="ticktick-root"` 且渲染 `TickTickShell`（不再复用旧 `.app-shell`）；`src/renderer/styles/ticktick.css` 已补齐 `.ticktick-root` / `.ticktick-app-shell` / `.ticktick-main` / `.ticktick-main-content` 的 `min-width:0` / `min-height:0` / overflow 规则。
- **真实状态**：**已修复待验收**（代码已落地，缺打包版可观察验收）。
- **最小验收标准**（可观察页面行为）：
  - 切到 TickTick 后主内容区占满侧边栏右侧，不再出现 ~12px 窄条。
  - 不出现整窗级横向滚动；侧边栏与主内容各自独立滚动。

#### P0-2 侧边栏工具区（专注计时 / 设置）定位（工具区定位）

- **文档现状**：仍描述为“被挤到底部、点击像打不开”。
- **代码核对**：`src/renderer/pages/ticktick/TickTickSidebar.tsx` 已移除 inline `marginTop:'auto'`，中间列表包进 `.tt-sidebar-scroll`、工具区改为 `.tt-sidebar-tools`；`ticktick.css` 已有对应 `flex:1 / min-height:0 / overflow-y:auto` 与 `flex-shrink:0` 规则。
- **真实状态**：**已修复待验收**（依赖 P0-1 一同在打包版确认）。
- **最小验收标准**（可观察页面行为）：
  - “专注计时 / 设置”固定可见，不随日历/清单内容滚走，无需滚到底。
  - 点击“专注计时 / 设置”后右侧主区稳定切换到对应页面。

#### P0-3 exe 双击打不开（启动环境）

- **文档现状**：与 `ELECTRON_RUN_AS_NODE` 环境变量相关，属环境问题而非业务代码 bug。
- **代码核对**：无业务代码修复项；打包/测试脚本不应设置或继承该变量。
- **真实状态**：**需 workaround / 文档收口**（非代码可闭环，靠启动前清理 + 文档说明收口）。
- **最小验收标准**（可观察启动行为）：
  - 新开 shell 后 `cmd /c set ELECTRON` 不再出现 `ELECTRON_RUN_AS_NODE`。
  - 双击 `release/win-unpacked/考研高数错题本.exe` 与 portable/免安装 exe 均能弹出窗口。
  - 文档中 workaround 说明清晰，实现者零上下文即可照做。

### P0 页面可见性验收范围

在 P0-1 / P0-2 判定为已闭环前，下列页面需逐一确认能显示真实内容而非空白：Today、Calendar、Inbox、List Detail、Focus、Settings。这是布局/定位修复的“实际生效”验收面，不引入新功能要求。

### 推荐修复顺序

1. **先验收 P0-1**（布局根容器）——它是 P0-2“点击像打不开”错觉的根因，必须先确认。
2. **再验收 P0-2**（工具区定位）——在 P0-1 通过的前提下确认切换与滚动。
3. **最后收口 P0-3**（启动环境）——独立于前两项，以文档 + 启动前清理收口。

P0 三项闭环后，本轮结束；P1/P2 的进入由后续单独计划决定，不在本文档展开。

## Risks

- 代码与文档可能已经部分脱节，容易把“曾经的问题”误当成“仍然的问题”。
- 如果没有把“已修待验收”和“未修”区分开，后续计划会重复劳动。
- 打包版启动问题可能仍然部分属于环境问题而非业务代码问题，需要单独标记。

## Acceptance Criteria

- 文档明确列出 TickTick P0 的当前问题清单。
- 每项问题都被归类为：
  - 已修复待重新验收
  - 尚未修复
  - 需以 workaround / 文档说明收口
- 每项问题都有最小验收标准。
- 文档结论能直接支撑下一步的实现计划。

## Task Breakdown

1. 重新核对 P0 问题清单与当前文档表述，标出文档与代码的漂移点（本轮已核对：P0-1 / P0-2 代码已落地但文档仍写“待修复”）。
2. 将问题分为“布局显示 / 工具区定位 / 启动环境”三类，各归为“已修复待验收 / 尚未修复 / 需 workaround 收口”。
3. 为每类问题写明真实状态与最小验收标准（可观察页面行为或启动行为）。
4. 给出推荐修复顺序（P0-1 → P0-2 → P0-3），作为下一步实现/文档同步计划输入。

## Verification

- 文档应能让实现者零上下文理解 P0 闭环目标。
- 文档只针对 TickTick P0，不扩到 P1/P2 或更大架构问题。
