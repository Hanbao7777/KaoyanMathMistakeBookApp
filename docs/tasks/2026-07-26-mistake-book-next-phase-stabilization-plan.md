# 错题本个人日用稳定版收口计划

## 状态与目标

**状态：方案已确认，待执行。**

本计划承接已关闭的 Agent Control Plane Phase C，将项目主线切回错题本本体。
当前目标不是公开发布，也不是继续扩大功能面，而是得到一个可放心日常使用、
出问题能定位、数据异常时能退回上一版的 Windows 便携版。

“个人日用稳定”不等于所有页面、所有 lint 和所有历史规划全部完成。本阶段只为
真实日用链路、数据安全和可回滚性设置硬门槛。

## 已确认的产品边界

以下决策已经用户逐项确认：

1. 目标是个人日用稳定版，不按公开发布标准收口。
2. 核心链路是：
   **Codex/MCP 导入测试错题 → 在应用中查找并查看 → 修改 → 完成一次复习 →
   撤销复习 → 重启后数据仍然正确**。
3. 备份必须实际恢复一次；验证只使用一次性测试数据。
4. portable EXE 是正式验收对象；win-unpacked 只用于调试，不重复承担正式验收。
5. 不做代码签名、安装程序和自动更新，升级时手动替换 portable EXE。
6. `reviewSession` 正确性仍是当前质量门槛；`masteryDisplay` 延后。
7. TickTick 只要求切换相关模式或页面时不崩溃；Kanban、Eisenhower、白噪音和
   其他深度功能不阻塞本阶段。
8. 不要求全项目 lint 清零，不把 lint 加为 CI 阻断项。只修真实缺陷涉及文件中的
   lint，或明显无用且低风险的代码。
9. 不做大规模结构重构。只有真实故障需要时，才做局部、可测试的小范围提取。
10. 数据丢失、程序崩溃、核心链路失败、重启后数据错误、备份无法恢复会阻断
    稳定版；排版、文字和低频功能小问题只记录，不阻断日用。
11. 所有自动测试和技术验收使用临时数据根，不直接操作
    `D:\KaoyanMathMistakeBook`。
12. 每个通过验收的 portable EXE 都记录代码版本、SHA-256、验收日期、核心结果
    和非阻断已知问题。
13. 技术验收完成后，由用户亲手进行约 5 分钟的最终日用确认。
14. 升级时保留上一版可用 EXE 和升级前备份；新版出现数据异常或核心故障时，
    立即退回上一版。
15. 远端同步采用独立稳定化分支先跑 CI，再决定是否同步 `main`。
16. GitHub 只建立一个“个人稳定版收口”总 Issue；只为正在执行的任务或发现的
    缺陷建立子 Issue。
17. 本轮只更新本计划。README、ROADMAP、KNOWN_ISSUES 和发布记录等到真实验收
    完成后再按结果更新。

## 明确排除

以下事项不进入本计划的任务、优先级或验收门槛：

- Claude Code token exchange 兼容性
- DeepTutor 评估或集成
- 内置 AI/OCR Beta 稳定化
- `masteryDisplay` 抽取
- TickTick 深度功能补齐
- 全量 lint 清零和 lint CI 门槛
- 大型模块结构性重构
- 代码签名、安装程序、自动更新和公开 Release

内置 AI/OCR 当前由 Codex 通过现有 MCP 错题导入能力替代。以上排除项只有在用户
重新改变产品范围后才会进入后续计划。

## 授权边界

本计划的确认只代表方案得到认可，不代表任何 GitHub 或发布写操作已经获准。
以下动作执行前必须再次取得用户明确授权：

- 创建、编辑或关闭 GitHub Issue、PR
- 推送稳定化分支或 `main`
- 发布 Release 或软件包
- 配置签名、证书、密钥或其他远端设置

未获授权时，可以完成本地检查、构建、临时数据验收、Issue 草稿和证据模板，
不得把这些内容写入远端。

## 执行计划

### P0-1：保护当前代码并获得 CI 结果

#### 执行

1. 核对提交范围和工作区状态，排除私有配置、生成物和本计划之外的修改。
2. 准备一个独立稳定化分支。
3. 经用户明确授权后推送该分支并运行 GitHub Actions。
4. 记录远端 commit、CI run 和 test/typecheck/build 结果。
5. 只有稳定化闭环完成后，才另行决定是否同步 `main`。

#### 验收

- 远端分支包含待验收代码且不包含本地私有配置或生成物。
- GitHub Actions 在同一 commit 上通过 test、typecheck 和 build。
- 推送和后续 `main` 同步均有各自明确授权。

### P0-2：portable EXE 核心链路验收

#### 数据安全

- 使用 `%TEMP%\kaoyan-*` 或其他一次性数据根。
- 不打开、迁移、恢复或修改 `D:\KaoyanMathMistakeBook`。
- 导入、编辑、撤销、删除和恢复操作只针对生成的 fixture 和测试数据。

#### 正式验收链路

1. 在干净临时数据根启动 portable EXE，完成首次初始化。
2. 通过 Codex/MCP 导入一条包含最小必要字段的测试错题。
3. 在错题库中找到它，打开详情并完成一次修改。
4. 提交一次复习结果，核对相关状态，再执行撤销。
5. 退出并重新启动 portable EXE，确认导入、修改和撤销后的最终状态仍正确。
6. 创建备份，在另一个隔离数据根中执行恢复，并核对恢复内容与保护备份。
7. 切换 TickTick 相关模式或页面，确认不会导致应用崩溃。

win-unpacked 可以用于定位启动、资源或日志问题，但其结果不能替代 portable
正式验收，也不要求重复执行整套链路。

#### 自动化策略

本阶段不强制先实现四条完整 Electron E2E。先执行真实 portable 人工验收，再按
观察到的风险补自动化：

- 能稳定、低成本自动化的核心回归，可以新增独立 `*.e2e.cjs` 场景文件。
- `tests/electron/launchElectron.cjs` 保持通用启动 helper，不堆入业务断言。
- 真实验收暴露的缺陷必须优先补最窄的回归测试。
- 视觉行为或系统文件对话框不适合稳定自动化时，保留简短人工检查记录。

#### 验收记录

每个候选 portable EXE 至少记录：

- 对应 commit
- EXE 文件名、路径和 SHA-256
- 验收日期
- 一次性数据根
- 核心链路逐项结果
- 备份恢复结果
- CI 结果链接或本地待填项
- 阻断问题与非阻断已知问题

### P0-3：数据回滚保障

1. 技术验收期间只使用测试数据。
2. 用户首次正常使用新版前，确认真实数据已有一份可恢复备份。
3. 保留上一版已知可用的 portable EXE，不用新版覆盖唯一副本。
4. 新版出现数据异常、崩溃或核心链路故障时停止使用，并退回上一版。
5. 不在真实数据上边用边调试恢复、迁移、回滚或删除逻辑。

### P0-4：用户最终确认

技术验收全部通过后，由用户启动候选 portable EXE，按自己的正常操作习惯进行
约 5 分钟确认。此时是在已有备份保护下正常使用，不是自动化或破坏性测试。

只有用户明确确认“可以日用”，该候选版本才可以标记为个人稳定版。

### P1-1：`reviewSession` 最小正确性回归

只处理会影响当前核心链路的共享逻辑：

- 准确率除零
- 复习统计撤销
- 知识点复习过滤

实现或修复时运行对应 focused test、`npm run typecheck` 和 `npm run build`。
`masteryDisplay` 不与本项捆绑。

### P1-2：TickTick 非崩溃冒烟

只验证打开相关页面、切换已存在模式时应用不崩溃。Kanban/Eisenhower 失败反馈、
Calendar 深度验收、白噪音实现或降级等均移出当前稳定版门槛。若冒烟发现崩溃，
按实际故障建立修复项和最窄回归。

### P1-3：按需 lint

不开展全仓 lint 清零，也不把 lint 加入 CI。仅在以下情况下修改 lint：

- 当前真实缺陷涉及的文件存在会妨碍修复或暴露明显错误的 lint；
- 本次改动新引入 lint；
- 可以确认是无用代码，且删除风险低、验证范围明确。

## Issue 与文档策略

在用户授权 GitHub 写入后：

1. 创建一个“个人稳定版收口”总 Issue，记录目标、完成定义和证据入口。
2. 只为正在执行的工作或验收发现的真实缺陷创建子 Issue。
3. 不为每个计划条目机械建 Issue，也不把 Issue 创建作为本地验收的前置条件。

本轮不修改 README、ROADMAP、KNOWN_ISSUES 或历史任务记录。个人稳定版完成后，
再根据真实 CI、验收和已知问题结果更新这些文档，避免提前宣称完成。

## 故障分级

### 阻断稳定版

- 数据丢失、错误覆盖或无法读取
- 应用崩溃或无法启动
- 核心链路任一步失败
- 重启后数据状态错误
- 备份不能恢复或恢复结果错误

### 记录但不阻断

- 不影响操作的小型排版或文字问题
- 明确不在本阶段范围内的低频功能缺口
- 有安全替代路径、且不影响数据正确性的轻微体验问题

非阻断不等于忽略：必须写入候选版本的已知问题记录，后续按真实使用频率决定
是否处理。

## 推荐执行批次

### Batch 1：本地准备

1. 重新核对 HEAD、工作区和测试基线。
2. 准备总 Issue 草稿和 portable 验收记录模板。
3. 准备稳定化分支，但不执行未经授权的远端写入。

### Batch 2：远端保护

1. 取得授权后创建总 Issue、推送独立分支。
2. 等待并记录 CI 结果。
3. CI 失败时只修与当前 commit 和稳定目标相关的问题。

### Batch 3：核心交付证据

1. 构建 portable EXE。
2. 使用临时数据完整执行核心链路和备份恢复。
3. 发现阻断故障时修复，并补最窄、稳定的回归测试。
4. 重建候选 EXE，记录 commit、哈希和复验结果。

### Batch 4：个人稳定版确认

1. 保存上一版 EXE 和真实数据升级前备份。
2. 用户完成约 5 分钟正常使用确认。
3. 记录最终结论和非阻断已知问题。
4. 用户确认后再决定是否同步 `main`，并更新 README、ROADMAP、
   KNOWN_ISSUES 和历史验收记录。

## 完成定义

个人日用稳定版完成必须同时满足：

- 独立稳定化分支已获授权推送，并在同一 commit 上通过 CI。
- portable EXE 已记录 commit、路径、SHA-256 和验收日期。
- 核心链路在临时数据根中全部通过。
- 备份已在独立临时数据根中成功恢复并核对。
- `reviewSession` 当前正确性问题已有 focused test 证据。
- TickTick 页面或模式切换不会造成应用崩溃。
- 没有未解决的数据安全、崩溃或核心链路阻断问题。
- 自动测试和技术验收未访问或修改真实数据目录。
- 上一版可用 EXE 和真实数据升级前备份均已保留。
- 非阻断问题已记录。
- 用户已完成约 5 分钟正常使用并明确确认可以日用。

完成定义不要求：win-unpacked 重复验收、四条完整 Electron E2E、全量 lint 清零、
`masteryDisplay`、TickTick 深度功能、大型重构、代码签名、安装程序或自动更新。
